# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Anubis is an AI personality reconstruction system — a LangGraph agent that reconstructs a person's identity from uploaded media (text, audio, images, video, PDFs, URLs, CSV) and serves as that person's AI avatar. The product name is "Neural Nexus."

## Architecture

### Graph structure (`src/anubis/graph.py`)

The exported `graph` (named `"Anubis"` in `langgraph.json`) is a two-level composition:

**Outer `message_workflow`** (entry point):
```
START → chat → resolve_human_message_images → anubis → END
```
- `chat`: extracts user/assistant IDs from config into `GlobalState`
- `resolve_human_message_images`: converts base64 image blocks to text descriptions

**Inner `anubis` graph** (loops until no tool calls):
```
START → load_consciousness → think ⇄ process_thoughts → END
```
- `load_consciousness` (`src/anubis/utils/nodes.py`): builds the system prompt dynamically from identity documents, recalled memories, and assistant context
- `think`: streams tokens to the client; if a tool call is made, returns `internal_thoughts`; otherwise attaches Go Emotions sentiment and returns final `messages`
- `process_thoughts`: `ToolNode` that executes identity tools, then loops back to `load_consciousness`

### Ambient vision (webcam / screen snapshots as hidden context)

The browser starts sending as soon as a webcam or screen share is live — no toggle; the sidebar eye only pauses. Snapshots ride the same `POST /message/{assistant_id}` call with `ambient=true` (plus `sources`, `captured_at`, `voice_mode`, `camera_facing`; a future microphone clip rides the same call). `enforce_ambient_request` (`src/api/webapp.py`) gates the turn (signed-in only, per-thread floor `AMBIENT_CAPTURE_MIN_INTERVAL_SECONDS` → 429 with `Retry-After`) and tags the `HumanMessage` with `additional_kwargs={"hidden": True, "kind": "ambient_observation", "ambient": {...}}`. In the outer graph, `resolve_human_message_images` describes the images with `DESCRIBE_AMBIENT_IMAGE_PROMPT` (keeping the tag and emitting `image_description_usage` events the API meters), then the `ambient_triage` node (`src/anubis/utils/ambient/triage_node.py`) classifies the observation as `ignore` (run ends; the hidden turn stays as context), `respond` (the deep agent replies), or `notify` (the deep agent writes a heads-up; `think` tags the reply's `response_metadata["ambient"]` so the frontend renders a card). The SSE stream carries an `ambient_decision` frame and repeats the decision on `done`; `GET /conversations/{thread_id}/messages` drops hidden turns unless `include_hidden=true`. Card decisions land in the store namespace `(user_id, assistant_id, "ambient_preference")` via `POST /ambient_preferences/{assistant_id}` and are recalled as precedent. **The avatar speaks on intent, not because a camera is on.** Sharing a camera is consent to be looked at, not a request to be spoken to, so the great majority of observations are noticed silently. Four things enforce that, because the classifier judges one observation at a time and has no sense of its own rate — an intentless `respond` repeated every interval is what turns a quiet webcam into a stream of interruptions. (1) The browser drops a frame that looks like the last one it sent for that stream (`isFrameMateriallyDifferent` / `shouldSendCapturedFrame` in `src/services/ambientCaptureScheduler.js`, thresholds in `src/config/ambientFrameChange.js`), so an unchanging room costs no description call and no triage call; `VITE_AMBIENT_QUIET_HEARTBEAT_SECONDS` still sends one frame every ten minutes so the avatar's picture does not go stale. (2) `AMBIENT_CLASSIFY_SYSTEM_PROMPT` requires a bid toward the avatar, something deliberately put in front of the avatar, or a world-facing camera; being visible is never a bid. (3) `ambient_triage` demotes a decision below `AMBIENT_RESPOND_SALIENCE_FLOOR` / `AMBIENT_NOTIFY_SALIENCE_FLOOR` to `ignore`, and demotes anything arriving inside `AMBIENT_RESPOND_COOLDOWN_SECONDS` of the avatar last speaking unless salience reaches `AMBIENT_RESPOND_COOLDOWN_OVERRIDE_SALIENCE` (`AmbientSpeechCooldown` in `observations.py`, a process-local singleton beside `AmbientThrottle`; only a decision that actually reaches the person starts the quiet period). A demoted observation is still kept as context — silence is not blindness. (4) A `respond` turn carries an `[AMBIENT_REASON]` line naming the one thing that justified speaking, so the avatar reacts to that thing instead of manufacturing significance.

**Which way the camera points changes what an observation means.** `camera_facing` normalizes to `self` or `world` (`normalize_camera_facing_value`, `observations.py`; `none` when only a screen was captured, `normalize_camera_facing`, `triage.py`) and reaches the classifier as `<CAMERA_FACING>`. A self-facing camera is the ordinary desk arrangement: the person is the subject, presence carries no request, and the respond rules apply strictly. A world-facing camera — a phone held up or worn on a lanyard, rear camera outward — is the person's own view, and aiming it outward is itself a standing request to be told what is in view, so being useful about the scene is the product rather than an interruption. A personal avatar treats that view as its own person's eyes; any other avatar treats it as looking at the world together with the person.

Compaction is the deep agent's `SummarizationMiddleware`, replaced by `AvatarSummarizationMiddleware` (`src/anubis/utils/middleware/avatar_summarization.py`), whose summary event is mirrored to `GlobalState.conversation_summary_event` so a compacted thread is not re-summarized every turn.

### Who is speaking (live voice turns labelled by speaker)

Live voice mode on a personal avatar sends each hands-free utterance as audio on the same `POST /message/{assistant_id}` call with `diarize=true` (plus `voice_mode=true`). `label_spoken_turn_files` (`src/api/webapp.py`) hands the recording to `diarize_spoken_turn` (`src/anubis/utils/voice/speakers.py`): one `gpt-4o-transcribe-diarize` call with up to four known speakers — the owner, cut from the voice-clone recordings (`avatar_voice_clips`, cached in-process), and up to `VOICE_SPEAKER_MEMORY_MAX_SPEAKERS` other people remembered per thread as clips in `avatar_voice_speakers` so "Speaker N" stays the same person. The script (`Evan: …` / `Speaker 2: …`) becomes the human turn's text and the `speakers` record lives in `additional_kwargs`. The avatar and the owner are one identity: owner lines are the avatar's own person speaking, other speakers (people or other avatars) are the conversation partners. The avatar's cloned voice is the owner's voice, so when the microphone picks the avatar's own playback up (another device, a speaker), `mark_avatar_echo` relabels owner-attributed lines that repeat the thread's recent AI replies (`_recent_avatar_reply_texts`) as `<name> (avatar)`; an utterance with no live owner speech is triaged rather than answered. An owner-only utterance is tagged `kind: spoken_turn` and answered directly; an utterance where someone else spoke is tagged like an ambient observation with `sources=["microphone"]` and `hidden: False` (it stays in the transcript) so `ambient_triage` decides ignore / respond / notify with the speech instructions (`RESPOND_INSTRUCTION_SPEECH` / `NOTIFY_INSTRUCTION_SPEECH`). The SSE stream announces the script as a `spoken_turn` frame right after `turn_started`; `load_consciousness` appends `SPOKEN_ROOM_CAPABILITY_PROMPT` once a thread holds a spoken turn. Diarization is metered as `api_metrics` inference type `diarization`. Env: `VOICE_SPEAKER_*` in `.env` / `.env.dev`. `VOICE_TRANSCRIPTION_PROMPT` biases whisper-1's vocabulary for live-voice utterances; it carries the product's own words ("webcam", "screen share", avatar and repo names) because whisper otherwise mis-hears them — "what's on the webcam" came back as "it's on the white cam".

**`owner_label` and `avatar_label` are two different names and conflating them was a live bug.** `owner_label` is the person at the microphone; `avatar_label` is the avatar. They are one person only on a *personal* avatar being talked to by its own creator (`_resolve_spoken_turn_labels`, `webapp.py`, decides which and passes `avatar_portrays_the_speaker`), which is also the only case where the stored reference clip identifies the *speaker* — the clip is the avatar's voice. On anybody else's avatar the clip is registered under the avatar's name instead, a voice matching it is the avatar's own playback, and the speaker is named from `your_name`, then their account, then "Owner". Before that split, the speaker label fell back to the avatar's name and `claim_lone_speaker_as_owner` claimed the one voice in the room as the avatar: Evan's own questions came back to him as `Shivon Zilis: what are you seeing right now?`. `mark_avatar_echo` relabels owner-attributed lines that repeat the thread's recent AI replies (`_recent_avatar_reply_texts`) as `<avatar name> (avatar)`; an utterance with no live owner speech is triaged rather than answered, and one that was *only* the avatar's playback says so instead of reading as silence. An owner-only utterance is tagged `kind: spoken_turn` and answered directly; an utterance where someone else spoke is tagged like an ambient observation with `sources=["microphone"]` and `hidden: False` (it stays in the transcript) so `ambient_triage` decides ignore / respond / notify with the speech instructions (`RESPOND_INSTRUCTION_SPEECH` / `NOTIFY_INSTRUCTION_SPEECH`). The SSE stream announces the script as a `spoken_turn` frame right after `turn_started`; `load_consciousness` appends `SPOKEN_ROOM_CAPABILITY_PROMPT` once a thread holds a spoken turn, plus `SPOKEN_ROOM_PERSONAL_AVATAR_PROMPT` when the avatar is a portrait of the caller — the unlabelled voice is then the avatar's own person, whose directions are carried out rather than answered, and saying that of somebody else's avatar is the prompt-side half of the same confusion. Diarization is metered as `api_metrics` inference type `diarization`. Env: `VOICE_SPEAKER_*` in `.env` / `.env.dev`. `VOICE_TRANSCRIPTION_PROMPT` biases whisper-1's vocabulary for live-voice utterances; it carries the product's own words ("webcam", "screen share", avatar and repo names) because whisper otherwise mis-hears them — "what's on the webcam" came back as "it's on the white cam".

The share is background context only, with one exception the avatar has to ask for. A typed or spoken message never carries a webcam / screen still (the browser's composer sends at once with only the person's own attachments, and nothing from the share is painted into the conversation); the avatar knows the screen through the hidden observations already on the thread. **Asked what it sees, the avatar takes a fresh look instead of reading an observation back.** Every turn reports what is live at that moment as the `live_shares` form field (`src/services/liveShareRegistry.js` publishes it out of `MediaShareContext`, which `MediaContext` cannot import back without a cycle). Three things read that field. `load_consciousness` adds a `<LIVE_SHARES>` section (`build_live_shares_block`, `observations.py`) naming what is shared right now and, for a source that is not, how old this thread's newest description of it is — without which the avatar narrates a screen the person stopped sharing as though it were still in view, because observations never expire. `mark_view_currency` (`observations.py`, applied to `model_facing_messages` in `graph.py`) then marks **each** observation `[CURRENT VIEW — …]` or `[EARLIER VIEW — … ]` with the reason it is no longer current (the share ended, a later look replaced it, or it has gone stale), because a summary section does not help when the observations themselves read as flat present-tense descriptions and the model has to tell one from another mid-thread. The marks are model-facing only and never written back to the thread: whether an observation is current is true of the moment it is read, not of the observation. A look taken this turn announces itself as superseding every earlier observation of the sources it covers. And `build_look_tools` (`src/anubis/utils/tools/vision/look_tools.py`) attaches the `look_now` tool whenever looking could matter — something is live, or the thread already holds scene observations, so the avatar can **check** whether a source is in view instead of asserting it (with nothing live the tool answers `not_shared` immediately, taking no pause and costing no capture). When something is live: the tool pauses the run with `interrupt({"kind": "look_now", "silent": true, "sources": [...], "open": [...]})`, the browser captures one frame per source (skipping the ambient loop's unchanged-frame filter and its ten-minute heartbeat — a look that was asked for is answered with the scene as it is) and resumes through `POST /message/{assistant_id}/resume` with `decision=looked` plus the frames, which `describe_look_frames` describes — with a per-source spec (`describe_look_prompt_for`, `schema.py`), because a camera still is about the person and a desktop still is about their work — and hands back as the resume value.

**A resume MUST carry the same share report the paused turn carried**, and this is the sharpest edge in the whole mechanism. The resumed run re-enters `think` and rebuilds every tool from the *resume request's* configurable, and `look_now` chooses between taking the pause — which is what collects the answer the request is carrying — and reporting that there is nothing to look at, purely from `live_shares` / `peekable_shares` / `may_control_shares`. A resume without them rebuilt a tool that believed the browser shared nothing, which returned `not_shared` before ever reaching the `interrupt`, and the frame the browser had just captured and paid to describe was discarded unread: the avatar opened the person's camera and then told them it could not see anything. `MediaContext` sends the report on the resume, and `LookContextRegistry` (`src/api/look_context.py`) remembers what each thread's last turn reported so a client that does not send it is still answered; `_look_context_for_resume` prefers the request and falls back to the memory. `tests/unit_tests/test_look_resume_context.py` is the regression. The pause raises no card and asks nobody to approve anything; `MediaContext` answers it itself and streams the continuation, capped at `MAXIMUM_LOOKS_PER_TURN` looks per turn. A conversation that never involved a camera never sees the tool, so ordinary messaging pays neither the tool's description nor the pause.

**The screen has three states, not two, and the middle one is the point.** *Off*; *peeked at* — a capture runs, the person chose in the browser's own picker exactly what it covers, and **nothing reads it until the avatar asks a question that needs a look**, then one frame; *shared* — the ordinary watched share, snapshotted on the interval. Peek and share are the same capture in different modes (`screenWatched` in `MediaShareContext`), so moving between them costs no second trip through the picker and only turning the capture off gives up the grant. `SidebarShareControls` offers both, beside each other, where the person already turns screen sharing on. A watched capture is reported as `live_shares`; an unwatched one as `peekable_shares` — that field *is* the difference between glancing and watching, and `captureAmbientStills` reads a screen only when `screenWatchedRef` is true.

**The camera works the other way round, and needs a stored permission because of it.** A granted camera permission persists on the origin, so the avatar really can reopen the camera on its own — `ShareControlSetting`'s switch (per browser, `src/config/avatarShareControl.js`, reported as `may_control_shares`) is what says whether it may, and `peekThroughCamera` opens it, takes one frame and closes it. The stream is never published as `webcamStream`, so no preview tile appears and the ambient loop never starts: **an avatar that may look is not an avatar that may watch.** There is deliberately **no stored permission for the screen** — a permission there would govern something that cannot happen without a fresh deliberate act anyway.

A screen the avatar cannot see still emits a `share_request` frame, and `ShareRequestPrompt` puts one button in front of the person whose press is the gesture — starting the capture in **peek** mode, because the avatar asked to see the screen once and answering that with continuous watching gives away more than was asked for. That button is deliberately **not** gated on `may_control_shares`: that permission is about the avatar acting on the person's device, and putting a button in front of someone is the opposite of acting on their device. Gating it meant a person who had never granted the camera could not even be offered a look at their screen. `stop_sharing` switches a camera or a screen off through a `share_stop` frame, which needs no answer and so takes no pause; a screen capture in either mode can be ended that way, while a merely-permitted camera cannot (a standing permission has nothing running behind it).

**The camera and the desktop are two views, not one "what can I see".** The camera answers questions about the person and their room; the desktop answers questions about what they are working on. `SOURCE_PURPOSE` names both in the tool description, in the look's result, and in the `<LIVE_SHARES>` section, so the avatar picks the source the question is about and says which one it is describing instead of answering one out of the other. The camera permission is per browser by design: a permission over one device's camera must not follow the account onto a device where it was never granted. The `share_request` frame is emitted *after* the `interrupt`, never before, because everything above the pause runs a second time on resume and the person must not be handed the same button twice. Observations yield to the person: `message_graph_sse` on a non-ambient turn calls `yield_in_flight_ambient_observations` (`src/api/message_stops.py`), which stops any observation still running on the thread (`ActiveMessageTurn.ambient`) and waits for `ActiveMessageTurn.finished` (bounded by `AMBIENT_OBSERVATION_YIELD_TIMEOUT_SECONDS`) before the graph run starts, so the two never write the thread's checkpoint at the same time; an observation stopped before triage is removed from the thread (`discard_ambient_observation`). An observation arriving while any turn is running on the thread is refused with 409 and `Retry-After` (`refuse_ambient_observation_on_busy_thread`), which the browser treats as pacing, not failure. The browser mirrors the same order: `yieldAmbientObservations` in `MediaContext.jsx` fires a stop for in-flight ambient turns before a typed or spoken turn, and the ambient loop treats the resulting abort as a quiet end.

**Talking to a personal avatar grows its voice, once it has a reference recording.** Each hands-free utterance is already diarized to produce the speaker script, so the owner's own windows are cut out of that same preprocessed audio (`cut_target_turns_to_mp3_data_uri`, no second diarizer call) and handed to `add_voice_clip` — the corpus grows while the person simply talks, `ensure_instant_voice` creates the clone the moment sixty seconds have accrued, and collection continues toward the professional clone. `POST /transcribe` contributes from dictation too, but whisper reports words and not who said them, so that path diarizes the recording against the stored reference clip first and keeps only the stretches matched to it — being the signed-in owner is not evidence that the voice on the microphone is the owner's. That is one diarization call per accrued utterance, metered like any other, paid off the reply path and only while the avatar is still collecting. Both paths run after the reply through `schedule_background`, so neither adds latency (`src/anubis/utils/voice/capture.py`).

**The reference audio clip is the gate, and nothing else is.** It is the anchor the diarizer matches voices against, so it is the only thing that can tell the owner apart from a third party or from background chatter in the room; without one `accrual_blocked_reason` is `reference_audio_missing` and nothing is stored — voice mode still transcribes and the avatar still answers. The reference is supplied deliberately (the settings recorder, a media upload carrying the owner's speech, or verified research) and **is never seeded from a live utterance**: a quiet owner in a room with a television would otherwise make a stranger's voice the avatar's voice, and the instant clone is built once and never rebuilt on its own. So that the very first live utterance can be attributed at all, `owner_reference_clip` falls back to the stored reference clip when the voice corpus is still empty. Three kinds of voice reach a microphone and any of them may be absent — often there is no avatar voice at all: only the person accrues, while avatar echo and every `Speaker N` segment are left behind. `claim_lone_speaker_as_owner` deliberately relabels a lone voice as the owner so a monologue is answered rather than triaged; accrual ignores that and reads `SpokenTurn.owner_matched_reference`, which records whether the diarizer itself matched the reference. Consent is asked once and kept on `avatar_voice.detail` (`POST /avatar_voice/capture_consent`), and clips carry a `voice_mode` source and a thread-stamped `source_document_name` so one conversation's contribution can be dropped with `forget_document_clips` and the clone rebuilt. `refresh_instant_voice_at_target` rebuilds a clone built from less than `ELEVENLABS_INSTANT_VOICE_CLONE_TARGET_SECONDS` exactly once when the corpus first reaches that target — the behaviour that setting's description always claimed but the code never did. `POST /transcribe` returns a small `voice` block so voice mode adopts a voice that finishes building mid-conversation instead of after a reload. Env: `VOICE_MODE_CAPTURE_*`, `INSTANT_VOICE_REFRESH_AT_TARGET_ENABLED`.

### How the person moves (wireframe motion learning)

The avatar's own person is wireframed — 33 named body joints and the 478-point face mesh — and how those named points move **through time** drives the avatar's words, stills, idle loops and lip-synced clips. Everything lives in `src/anubis/utils/motion/`; nothing motion-related touches the LangGraph store (the store embeds every value at 640 dims). Coordinates arrive from any **source** and the source matters nowhere past capture: `live_camera` (the browser runs MediaPipe `PoseLandmarker` + `FaceLandmarker` in WASM — `src/hooks/useMotionWireframe.js`, `src/services/motionWireframe.js` — and rides each window on the ambient `POST /message/{assistant_id}` as the `motion_track` form field, or on `POST /avatar_motion_tracks` when the scene did not change enough to send a still), `uploaded_video` (`_learn_motion_from_video` in `process_media_graph/utils/nodes.py`, **video only**, beside the voice-clip collection; frames via ffmpeg, the same two models server-side in `motion/landmarker.py` + `video_tracks.py`, in a worker thread), `generated_clip` (the platform's own output, scored, never learned from) and `neural_decoder` (a motor-cortex decoder's coordinates — CRCNS MC-1 style — proved by authentication, not sight). The landmark set is **versioned and declared** (`landmarks.py`, `LANDMARK_SETS`, `MOTION_LANDMARK_SET_VERSION`): every row records its version, so a denser set (hands, iris, a decoder's limb set) is a registration and a bump, never a rewrite.

**The identity gate fails closed** (`motion/identity.py`, `verify_identity`): a camera window is attributed only when the camera faces the person (`self`), the avatar is the caller's own personal avatar, and a vision comparison of the frame with the reference image (`MOTION_SUBJECT_IDENTITY_PROMPT`, `confirm_person_matches_reference`, cached per session for `MOTION_IDENTITY_REVERIFY_SECONDS`) says same person, the focus, above `MOTION_IDENTITY_MIN_CONFIDENCE`; uploaded video needs only the vision match, per window; a classifier outage drops the window. A mean cannot describe movement, so the representation has four tiers (`service.record_motion_window`): **Tier 0** raw frames split into rigid head pose, pose-free face residual (`normalize.canonicalize_face`, mirrored exactly in the browser) and shoulder-width-normalized body; **Tier 1** a per-avatar PCA **expression basis** (`basis.py`, `IncrementalPCA`, `MOTION_BASIS_COMPONENTS`) fitted from the raw **golden** set once `MOTION_BASIS_MIN_SECONDS` exist — a component is whatever vertices covary on *this* face, described by region geometry (`describe_component`), and what makes 478 points cost ~376 B a frame; the browser fetches it from `GET /avatar_motion_basis` and encodes locally; **Tier 2** **primitives** (`primitives.py`): the timeline cut into events by hysteresis on speed (a pause at a gesture's apex is joined, `_JOIN_GAP_SECONDS`), resampled, clustered, each keeping its **prototype trajectory** per named coordinate over normalized time, with duration, amplitude and context (speaking / listening, emotion); **Tier 3** scalars (`measurements.py`: blink rate from the eye aspect ratio, resting head roll, gesture rate, lean, sway…) folded as seconds-weighted running means **with variance and sample count** (`signature.py`). Tables (`motion/repository.py`, created on boot beside the media assets): `avatar_motion_tracks` (float16 buffers, `MOTION_TRACK_RETENTION_SECONDS_PER_AVATAR`, pruned oldest-first per emotion), `avatar_motion_golden` (raw mesh, `MOTION_GOLDEN_SECONDS_PER_AVATAR`, curated for identity confidence and emotion coverage — its job is to outlive any refit), `avatar_motion_basis`, `avatar_motion_primitives`, `avatar_motion_signature`, `avatar_motion_profile`.

**Numbers become words without a model** (`motion_prompt.py`): scalars pass through band tables, primitives are phrased from the shape of their prototype and their timing, and anything under `MOTION_SIGNATURE_MIN_SECONDS`, too variable for its mean, or seen fewer than `MOTION_PRIMITIVE_MIN_OCCURRENCES` times is **omitted** — only converged habits speak. The rendered HEAD / EYES / POSTURE / HANDS / FACE block per emotion is cached on `avatar_motion_profile` and consumed four ways: `=== HOW YOU MOVE ===` in the ROLE (`read_how_you_move_section`, one primary-key read in `load_consciousness`), `still_prompt_for(..., motion_prompt=)` (carriage lines only), `idle_loop_prompt_for(..., motion_prompt=)` (replaces the generic breathe-blink-fidget clause), and the **`prompt` field of the lip-sync generation** — `creatify-aurora`'s documented behavioural channel (gestures, head, gaze, demeanour), composed as a cinematic line (`LIP_SYNC_CINEMATIC_PROMPT`) plus the block (`lip_sync.build_lip_sync_prompt`), keyed into the clip cache so a matured profile renders a new clip, and retried once without the field if the vendor model refuses it. A finished clip is wireframed with the same extractor and scored against the person (`service.record_fidelity` → `motion_fidelity` on the profile): the actual-versus-predicted comparison, per scalar and per prototype. `GET /avatar_motion_profile` and `DELETE /avatar_motion_tracks` back the "How you move" settings panel (`MotionProfilePanel.jsx`). Env: the `MOTION_*` / `LIP_SYNC_PROMPT_*` block in `context.py`; `VITE_MOTION_*` in the frontend. Real-time reenactment from the live mesh is the stated next step, not built; Tier 0 and Tier 2 are what it would consume.

### State and Context

- **`GlobalState`** (`src/anubis/utils/state.py`): LangGraph `TypedDict` with `messages`, `internal_thoughts`, `system_message`, identity documents, media upload queues, and model metrics
- **`GlobalContext`** (`src/anubis/utils/context.py`): LangGraph `context_schema` dataclass. `__post_init__` auto-reads env vars by uppercasing field names. **Every new env var must be added to both `.env` / `.env.dev` (uppercase) and as a field here (lowercase)**, then accessed only via `GlobalContext()` — never `os.environ` directly in business logic

### Store namespaces (LangGraph cross-thread store)

Three namespaces are used by identity tools (`src/anubis/utils/tools/identity/identity_tools.py`):
- **`memory`**: episodic events from conversation; retrieved by similarity query per conversation
- **`identity`**: primary-source facts (YouTube transcripts, tweets, uploaded documents); all loaded every turn without limit
- **`quote`**: verbatim historical quotes used for few-shot style grounding; top-K retrieved per turn

**Continuous learning** (`src/anubis/utils/learning/`) adds per-`(user_id, assistant_id)` namespaces read into dedicated system-prompt sections every turn: `engagement` (scalar counters), `feedback` (user-written feedback messages), `rating_positive` / `rating_negative` (avatar messages the user liked / disliked, keyed by message id), `sentiment` (`current:{thread_id}` scalar running summary + `history:{thread_id}` embedded summaries), `what_feels_real`, and `preference`. Pending-sweep markers live under `("learning_pending", user_id)` keyed by thread id. The outer graph node `observe_user` (parallel to `resolve_human_message_images`, joined by `join_user_observation`) records engagement, immediate Go Emotions sentiment, and the running conversation summary; the lifespan task `run_learning_sweeper` finalizes sentiment history, folds ratings into preferences, and infers preferences once an account is idle (`LEARNING_*`, `ASK_WHAT_FEELS_REAL_AFTER_MESSAGES`, `CONVERSATION_SENTIMENT_PER_TURN_ENABLED` env vars). Tools `learn_user_preference` and `record_what_feels_real` (`tools/identity/learning_tools.py`) capture dictated preferences and realness statements. The browser-facing row for each rated reply stays in `message_feedback` (`src/anubis/utils/message_feedback.py`: thumb, feels-real mark, note, rating score); `POST /message_feedback` accepts `feedback_type` in `like|dislike|rating|comment|feels_real|feels_fake` and writes both the row and the learning records, `GET /avatar_preferences/{assistant_id}` returns the rows plus `learned_preferences`, `feedback_messages`, and `what_feels_real`, and the `like` / `dislike` / `feedback` form fields on `POST /message/{assistant_id}` are live. Both feedback routes accept anonymous visitors (`get_current_user_or_anonymous_user`): a visitor's records live under the visitor's hashed address, and the rated thread is read back with the anonymous key.

The store's vector index is configured in `langgraph.json` (not code): it auto-embeds `document.kwargs.page_content` with `huggingface:microsoft/harrier-oss-v1-270m` at **640 dims**. Anything written to the store must stay consistent with that model/dimension.

### Passive psychological analysis (the avatar's learned psychology)

Uploading media reads the target's latent psychology and feeds it back into every reply. `psycho_analysis_graph` (`src/subgraphs/psycho_analysis_graph/`) is a fourth parallel branch off `convert_media_list_to_text_document` in `process_media_graph`. `select_target_documents` keeps only documents carrying the target's own words (`target_name` present, `is_target` not false, not `proprietary_content`), capped by `PSYCHOLOGICAL_ANALYSIS_MAX_DOCUMENTS` — the biggest cost lever, since every document costs one structured-output call per dimension. Then **one node per dimension runs concurrently**: `love_languages` (expressing vs receiving), `dialogue_emotional_triggers`, `emotional_baseline`, `attachment_style`, `schwartz_values`, `moral_foundations`, `cognitive_style` (reasoning pattern, abstraction, ambiguity tolerance, and the biases the target actually runs on), `myers_briggs`, `personality_archetypes`, `defense_mechanisms`, `core_motivations`, `conversation_subtleties`, and `dark_traits` (off by default).

`dialogue_emotional_triggers` reads a different queue from the rest (`reads_full_dialogue=True`): a trigger is a stimulus and a reaction, and the analysis queue's few-hundred-character target-only chunks rarely contain both, so it reads the adapter queue's unchunked role-converted conversation instead. Measured on one interview, that is the difference between one trigger and eight. Its store record embeds ONLY the generalized trigger description, because the store index embeds `page_content` and anything else in there drags every trigger toward the same middle distance — with the emotion and response folded in, an unrelated question about the weather scored higher than three of four genuine matches. `DEFAULT_TRIGGER_MATCH_MINIMUM_SCORE` is calibrated against the embedding model in `langgraph.json` and must be re-measured if that model changes.

The twelve pre-existing trait analyzers in `latent_feature_analysis_prompts.py` are all bespoke; ten of them ran on a generic `build_stub_feature_prompt` template until 2026-09-10. Every one now carries a `<division_of_labour>` block naming what the other analyzers own, because independent extractors reading one document otherwise all seize the most salient passage and restate it in their own vocabulary — the same observation came back as a value, a want, a need, a flaw and a history finding. A dimension is *graded* (a fixed trait list scored zero to one against `ScoredPsychologicalDimension`) or *narrative* (free-form findings through the existing `LatentFeatureAnalysisClass`); adding one is a prompt plus a line in `PSYCHOLOGICAL_DIMENSIONS` (`utils/dimensions.py`).

Findings land twice. Raw findings go to the `analysis` namespace and reach `=== ANALYZED TRAITS ===` by similarity like every other analyzed trait; `consolidate_psychological_profile` also folds them into one accumulated record per avatar at `(creator_id, assistant_id, "psychological_profile")` key `current`, which `load_consciousness` reads by key (through `aget_through_cache`, inside the existing `asyncio.gather`) into a dedicated `=== PSYCHOLOGICAL PROFILE ===` section — because how a person gives affection or reacts under strain bears on *every* reply, not only topically similar ones. The profile **accumulates**: a graded trait keeps a confidence-weighted running mean across uploads, so a second upload reinforces or moves a score rather than replacing it.

`=== YOUR EMOTIONS ===` is now real. `(creator_id, assistant_id, "current_emotion")` holds an eight-emotion Plutchik wheel plus the baseline read from media. `observe_user` advances it every turn (`src/anubis/utils/psycho/current_emotion.py`) using signals the turn already computed — the Go Emotions reading of the incoming message, and any stored trigger the message matches by similarity in the `emotional_trigger` namespace — so it adds **no model call**; between turns it decays toward the baseline on `CURRENT_EMOTION_DECAY_HOURS`. The owner corrects the profile in conversation with `correct_psychological_profile` (`learning_tools.py`), which is in `IDENTITY_TOOLS` so the prompt refreshes in the same turn.

The pre-existing `analyze_documents` fan-out is switched on (`ENABLE_DOCUMENT_ANALYSIS=TRUE`) now that `default_scaffolds_for_document` (`analysis_methods.py`) picks a document's analyzers from its `classified_situation` instead of running all fifteen on everything; `standardized_questions` (~200 calls for one document) is restricted to biographical documents and gated behind `STANDARDIZED_QUESTION_ANALYSIS_ENABLED`, default FALSE.

### AI monitoring (content moderation and account bans)

Every message and every upload is screened against the terms of service and the privacy policy. `moderation_graph` (`src/subgraphs/moderation_graph/graph.py`) is `fast_screen → route_after_fast_screen → refuse | deep_judge | END`: stage one is OpenAI's free `omni-moderation-latest` (always the OpenAI client regardless of `MODEL_PROVIDER`, like the speech APIs), stage two the structured-output judge over `PRIVACY_POLICY` / `TERMS_OF_SERVICE`. **Both stages are fail-open** — a classifier outage must never lock every person out, because the consequence is a ban.

The two paths differ deliberately. **Chat costs no latency**: `moderate_content_fast` is a third parallel branch off `chat` joining at `join_user_observation`, and only a hard block (a category at or above `CONTENT_MODERATION_FAST_SCREEN_THRESHOLD`) refuses inline via `refuse_for_violation`; the deep judge runs *after* the reply has streamed, from `_judge_message_after_reply` under `schedule_background`, so enforcement lands on the caller's next request. **Uploads gate instead**: `moderate_documents` (`moderation_graph/media_node.py`) sits between conversion and the fan-out, because content that violates the terms must never be indexed, analyzed, or turned into training data — and an upload is already a background job nobody waits on. Set `configurable["skip_content_moderation"]` whenever the graph is re-entered with words that are not the account holder's own (a live-stream viewer, a harvested turn), mirroring `skip_observation`.

The API layer owns the consequences, because they need the pool and the Stripe client the graph does not hold: the `moderation_violation` SSE frame and `run_batch_media_job`'s `on_moderation_violation` callback both call `ban_account` (`src/security/bans.py`). The `banned_accounts` table is the **only** source of truth — Auth0 is never written — and a ban cancels the Stripe subscription and refunds the latest paid invoice (`BAN_REFUND_ENABLED`). `refuse_if_banned` refuses at signup, API-key resolution, and the anonymous path, so anonymous visitors are banned by hashed IP; `usable_hashed_ip` drops the development-mode hash, which every local caller shares. `GET /ban_status`, `GET /admin/bans`, `POST /admin/bans/{ban_id}/lift`.

### Content subscriptions (the personal avatar's own accounts, crawled and subscribed)

Connecting an account the owner **owns** proves it, walks what they have already published, and subscribes so the next thing arrives on its own. Personal-avatar only: these accounts are a claim about a real person, and only the avatar depicting its own creator can make one.

**Ownership is the prerequisite everything rests on** (`connected_accounts/ownership.py`). An OAuth sign-in proves itself (the vendor names who signed in); a signed-in browser session proves itself one step later (the handle is *read* off the account's own page, not asserted); a feed or profile address proves nothing, and stays `unproven` until the owner places the issued token in it or links back with `rel="me"` from an account already proven. Unproven means connected and usable in conversation while contributing **nothing** to identity — content from an account nobody proved is theirs would teach the avatar to speak as somebody else. `is_owned_by_personal_avatar` is the single gate, and both the crawl and the intake consult it.

**Updates are event-driven, never polled.** The transport is a property of the platform, declared on the provider row (`content_transport`), not of how the account was connected: YouTube connects by OAuth and announces by WebSub; Instagram connects by browser session and announces through Meta's webhook. Platforms offering no webhook anyone can have (X, TikTok, LinkedIn) still **email the owner when the owner publishes**, and that mailbox is already connected and watched — so the notice is the event. That is why mail and social share one table and one intake. A platform that can do neither is reported as *not subscribable* rather than swept on a timer.

**Mail is event-driven too.** `inbox/idle_watchers.py` holds an IMAP IDLE connection per mailbox so the server speaks first; `poll_forever` stays as the catch-up pass (IDLE keeps up, the poll catches up), and a server refusing IDLE degrades into that poll on its own.

**One intake, always metered** (`subscriptions/intake.py`): dedupe on the platform's own content id (every push transport redelivers, and the same video legitimately arrives as both a webhook and an email), check ownership, then hand the address to `start_identity_media_job_from_chat` — the same path an interactive upload takes, and the only one running the tier gate, allotment, rate limit and Stripe meter. Never pass `bootstrap=True` there; that flag is the avatar-creation exemption. Background work resolves the owner with `get_user_by_identity_user_id` (no `Request`) and reads the avatar's name from the `assistant` table directly, because the LangGraph SDK client needs a caller's plaintext API key that nothing unattended holds.

**The initial crawl is breadth-first and prunes** (`subscriptions/crawl.py`). A profile links to their posts and their posts link to the whole internet, so a page that is not about this person is not merely skipped — its links are dropped, because they lead further away. `PersonalAvatarRelevance` (`schema.py`) judges each node, and the walk is bounded three ways at once: a per-tier item cap, `SOCIAL_CRAWL_MAX_DEPTH`, and `SOCIAL_CRAWL_MAX_NODES`. It reuses `URLDocumentLoaderClass._classify_url`, so a YouTube channel still enumerates into individual videos.

**The callback cannot be authenticated** — the caller is YouTube, not the owner — so the signature is the only thing between an announcement and the avatar's identity. `POST /social_webhook/{provider}` verifies against the **raw body before parsing** (a payload re-serialized after parsing is no longer what was signed), enforces a freshness window, and refuses a topic this server never asked about. `SOCIAL_WEBHOOK_CALLBACK_BASE_URL` must be a public https address; empty disables push transports while notification transports keep working. WebSub leases expire silently, so a renewal task refreshes them — a timer over stored expiry times, not a poll.

Routes: `/social_subscriptions` (what is proven, what is subscribed, what arrived), `.../verify`, `.../pull_more`. `REQUIRE_SOCIAL_PROOF_FOR_SHARING` makes `/share_avatar` require a proven social account — default FALSE, because turning it on refuses sharing for an already-shared avatar with no connected account.

### Audio & diarization pipeline (`src/anubis/utils/utility.py`)

Speech APIs **always use the OpenAI client** (`_openai_client_for_speech`), independent of `MODEL_PROVIDER` — they need `OPENAI_API_KEY` (falls back to `llm_provider_api_key`).
- **Transcription** (`transcribe_audio`): OpenAI `whisper-1` (`audio_transcription_model`). Files larger than `whisper_max_bytes` (25 MiB) are split into segments and transcribed in chunks, then stitched.
- **Diarization** (`transcribe_audio_diarize`): OpenAI `gpt-4o-transcribe-diarize` with `response_format="diarized_json"`. A **reference audio clip** of the target speaker is passed via `known_speaker_names` (`audio_diarization_known_speaker_name`) so the target's turns are labeled. Reference audio is truncated to `reference_audio_diarize_max_seconds` to stay within a **single non-chunked diarizer call**, keeping speaker labels unified across the timeline; `isolate_dominant_speaker_audio_b64` extracts the dominant speaker for grounding.
- **Preprocessing**: `noisereduce` (spectral-gating) + `librosa`/`soundfile`; `demucs`/`deepfilternet` paths exist but are currently disabled. `extract_video_audio_b64` pulls audio out of uploaded video via moviepy.
- All audio env vars live under the "Audio Transcription & Diarization Model" block in `context.py` (pricing, model names, byte/second caps).

### API (`src/api/webapp.py`)

FastAPI app with SSE streaming on `POST /message/{assistant_id}`. The stream opens with a `turn_started` frame carrying the `request_id`; `POST /message/{assistant_id}/stop` (form `request_id` or `thread_id`) ends a reply that is still generating — the stream then finishes with a `done` frame flagged `stopped`, the partial reply is written to the thread as the `anubis` node's output, and the estimated usage is metered (`src/api/message_stops.py`; a client disconnect is finalized the same way in a background task). Configured as the LangGraph HTTP app in `langgraph.json`. Authentication via Supabase JWT + Auth0 (`src/security/auth.py`); Stripe for subscription checks.

### Model initialization (`src/anubis/utils/model.py`)

`init_model()` dispatches to provider-specific SDK imports lazily based on the `MODEL_PROVIDER` env var — accepted values are `OPEN_AI`, `TOGETHER`, `NVIDIA`, `META` (Llama, via the OpenAI-compatible endpoint). All model providers must be configured via `GlobalContext` fields. Note speech (transcription/diarization) bypasses this and always uses OpenAI directly.

### Observability

Prometheus metrics are exposed on the FastAPI app. Grafana dashboard provisioned via `grafana/provisioning/`. Dev compose does not run Grafana/Prometheus; prod compose (`docker-compose-prod.yml`) does.

## Key conventions

- **Prompts**: follow the OpenAI GPT-5 prompting guide conventions
- **Env vars**: define in `.env` + `.env.dev` (uppercase), add a `field(default=None, metadata={"description": "..."})` in `GlobalContext` (lowercase), access via `context = GlobalContext()` at the top of functions and pass through nested calls
- **Imports for cold-start perf**: heavy SDK imports (`langchain_community`, provider SDKs) must be lazy (inside functions or conditional branches), not at module scope — several imports were already moved to avoid 7–13 s cold-start penalties
- **`internal_thoughts`**: parallel to `messages`; used for the agent's tool-call loop so tool turns don't emit `assistant_token` stream events meant for the user
